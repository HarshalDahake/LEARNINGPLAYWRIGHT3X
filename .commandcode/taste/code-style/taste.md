# code-style
- When the user says "fix the bug in my code", they expect the assistant to directly edit the file to apply the fix (in the JS learning files), not just suggest changes for the user to apply themselves. Confidence: 0.50
- In JS learning files, when the user proposes an experiment ("Try Student.display(\"Harshal\") and log the parameter instead of this.name"), they expect the assistant to directly edit the file to apply the variation and explain the resulting output, not just describe the change. Confidence: 0.55
- In the JS learning files, prefers modern ES module `import`/`export` syntax over CommonJS; when an `import` fails because the root package.json is `commonjs`, resolve it by adding a nested `package.json` with `"type": "module"` in the nearest folder (keeping only that minimal change) rather than switching the code to `require`. Confidence: 0.62
- When explaining/contrasting two similar concepts (e.g., spread `...num` vs rest `...codes`), present the comparison in a table format with clear columns (where it appears, position, name, behavior, result). Confidence: 0.60
- When adding concept documentation to comment blocks in JS files, follow the user's existing bullet-style (`- ` prefix) pattern rather than inventing new formatting. Confidence: 0.60
- In JS learning files with a concept comment block above a program, annotate each listed point with text markers like `[covered in program]` / `[not covered]`, NOT with ✔/✘ symbols. When a file lacks the concept block entirely, add the full block. Adapt the covered/not-covered markers to what each program actually demonstrates (e.g., `[not covered - no break used]`). Confidence: 0.97
- When updating the comment section in JS learning files, apply changes to the comment section only, not to the program code, and do NOT propose/insert additional example programs. Confidence: 0.78
